Hebrew filenames broke uploads. Two files, no SQL.

THE CAUSE
The storage key was built as `<season>/<uuid>-<original filename>`, and
Supabase Storage keys only accept letters, digits and a few punctuation marks.
Hebrew is rejected outright with "Invalid key", which is what every
screenshot-named receipt hit — "צילום מסך 2026-09-17 213755.png" can never be
a valid key.

THE FIX
The key is now `<season>/<uuid>.<ext>` — only the extension is kept from the
original name.

I deliberately did NOT transliterate or strip the name. Stripping Hebrew leaves
a key like "----.png", which is worse than one that is plainly an id, and
transliteration guesses at something nobody reads: the uuid already makes the
key unique, and the user finds a receipt by its number and its transaction,
never by this path.

A SECOND BUG THIS EXPOSED
The receipts ZIP derived its filename with `split('.').pop()` on the WHOLE
path. With no extension that returns the season folder, so a file would be
named "1043.2027/". It was nearly unreachable before, because an uploaded name
almost always carried an extension — and my change makes extension-less keys
possible. It now reads the last path segment and falls back to ".bin".

NOT AFFECTED
The receipt preview decides pdf-vs-image by reading the file's actual bytes,
not its extension, so it behaves the same.

ALREADY-UPLOADED RECEIPTS ARE UNTOUCHED. Their keys stay as they are and keep
resolving; only new uploads use the new shape.

After deploying, index.html should reference the fingerprint above.
