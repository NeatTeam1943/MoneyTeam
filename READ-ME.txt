Found it, and this time the trace pointed straight at it.

WHAT THE SCREENSHOT SHOWED
    budgets_guest        200   6889 bytes
    ledger_lines_guest   200   3681 bytes
    transactions_guest   200   3702 bytes

Every request succeeded. The data was arriving and the screen was still empty,
which meant the fault was after the fetch, not in it.

THE CAUSE
    Dashboard.jsx     const uid = session?.user?.id || (isParent ? 'guest' : null)
    Transactions.jsx  const uid = session?.user?.id || (isParent ? 'guest' : null)
    Budgets.jsx       const uid = session?.user?.id          <- no fallback

A guest has NO session: migration 18 made guest mode work without signing in.
So on the budgets page `uid` was null, the effect keyed on it skipped, and
load() never ran. The successful requests in the trace were fired by the other
two pages — which is why the network tab looked healthy while the page showed
nothing.

It is now the same line as the two pages that always worked. I did not invent a
third shape for it.

WHY IT TOOK SO LONG
I checked the view, the grants, the RLS and the query branching — all of which
were fine — and never checked whether the load ran at all. The lesson is in the
check below.

TWO CHECKS ADDED, BOTH PROVEN BY SABOTAGE
  · a guest-reachable page must derive uid with the 'guest' fallback
  · a guest-reachable page must not query a member-only table unbranched

The second one flagged a correct line on its first run, so I taught it to
understand `if (isParent) return` rather than leave a noisy check — one people
learn to ignore is worse than none.
